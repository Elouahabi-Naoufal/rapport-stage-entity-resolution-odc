\section{Leçons d'Ingénierie}

\begin{enumerate}
    \item \textbf{Le blocage façonne tout} : les règles de blocage ne filtrent pas seulement les comparaisons — elles entraînent le modèle EM. Un mauvais blocage (ex : \texttt{CODE\_BANQUE\_BAM + ANNEE + SENS}) enseigne de mauvaises leçons qui corrompent toutes les prédictions en aval.

    \item \textbf{Mesurer avant d'agir} : un script de diagnostic du blocage (mesure des paires générées par règle) prend 10 minutes à écrire et révèle immédiatement les méga-blocs. Sans ce diagnostic, des heures de débogage seraient nécessaires.

    \item \textbf{Les contraintes dures battent les features douces} : la règle de veto RC est une logique métier triviale, mais elle élimine toute une classe d'erreurs qu'un modèle ML complexe aurait du mal à gérer.

    \item \textbf{Les données synthétiques doivent être algorithmiquement réalistes} : des données visuellement plausibles peuvent être toxiques pour un algorithme ML. La distribution Zipfienne sans cap générait des entreprises avec 3\,000+ déclarations — statistiquement impossible et computationnellement catastrophique.

    \item \textbf{La stratégie hybride \_R / dirty est indispensable} : les anciens enregistrements sans colonnes \texttt{\_R} doivent être traités par des règles de fallback sur les champs bruités. Ignorer ce cas revient à exclure une partie significative de l'historique.
\end{enumerate}

\section*{Conclusion}

Ce chapitre a démontré que le pipeline atteint des performances solides sur un benchmark synthétique réaliste. Le recall de 100\,\% garantit qu'aucun vrai match n'est raté. La précision de 72,7\,\% avec Splink seul, améliorable à 85--90\,\% avec XGBoost, constitue une base solide pour une mise en production progressive. La prochaine étape est la validation sur les données historiques réelles de l'Office des Changes.
